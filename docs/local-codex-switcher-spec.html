01 · Product contract

Local Codex Switcher · proposed v0.1.0. One deliberate account change, with protected credentials and an honest result.

Outcome

A local desktop utility lets the owner add authorized ChatGPT/Codex accounts, choose one, close the affected official desktop application, preserve the latest outgoing credentials, install the selected credentials, and reopen that same application. It must never submit a model prompt or route inference. This is an account-handoff tool, not an account pool, provider gateway, quota optimizer, or security boundary between workspaces.

Scope and assumption

Design targets Windows and macOS, with independent release qualification for each. Use Windows 11 x64 and macOS arm64 as the initial test lanes, not claims of supported installed versions. Linux, WSL, remote machines and multi-instance Desktop operation are outside v0.1.0. A Windows/WSL mismatch is a blocker, not an invitation to copy across environments.

Authority

This specification is normative for the proposed product. Research findings explain design choices but do not authorize feature expansion. MUST requirements are release gates. No live Codex installation or real OAuth session was tested for this packet; no desktop/runtime build is prequalified. Phase Q0 must establish the actual supported contract before any auth mutation is enabled.

External baseline

OpenAI currently documents web account switching as unavailable in Codex desktop. Codex authentication is not universally an auth.json-only contract. App-server provides an official-runtime integration surface, but launching our own helper does not prove a running Desktop changed identity. Compatibility is therefore tied to exact qualified builds. O1 O2 O3 O4

Success in plain language

The selected account becomes the account the reopened official app uses; the previous account remains reusable unless the provider has invalidated it. A failure must leave either the original account safely installed or a clearly explained, recoverable state. The UI distinguishes installation, credential acceptance and actual Desktop confirmation instead of collapsing all three into a green check.

Why a WebView is acceptable here

This is a practical cross-platform choice, not the minimum conceivable dependency count. The WebView only displays non-secret metadata and sends narrowly typed user intents. The Rust core revalidates every operation and owns native confirmation. A future native-shell replacement may reuse the core without changing the transaction contract. Tauri capabilities are an additional restriction, not a substitute for backend checks. T1

No inference or routing

The switcher MUST NOT implement an HTTP/SSE/WebSocket inference proxy, submit turn/start or codex exec requests, warm up quota windows, redeem credits, send account emails, schedule account rotation or replay tasks. A login callback listener created by the official runtime is a documented exception to the no-listener rule, limited to interactive onboarding.

03 · Compatibility gate

No filename, process name or package path is universal. Qualification records are evidence, not guesses.

F-004 · MUST

Discover without changing

First launch performs read-only inventory. Show the exact official application identity, package/bundle ID, executable path, version/hash, OS/architecture, runtime path/hash, effective Codex home, configured backend and policy source status. Candidate discovery may search standard installations, but execution requires user-approved binding to a verified official installation. Never execute the first codex found on PATH or source a login shell.

F-005 · MUST

Effective home and configuration

The adapter must establish the home and auth backend used by the selected Desktop build, not just the switcher shell environment. Read documented configuration layers and version-pinned defaults with the qualified runtime/adapter; detect CODEX_HOME, environment/API-key auth, managed forced-login/workspace restrictions and unsupported external credential sources. Incomplete evidence is E_COMPAT_UNKNOWN. Permission denied is not absence.

Backend refusal

Only a positively established effective file backend is eligible in v0.1.0. auto is unsupported even when a fallback auth.json exists. Existing keyring state is not deleted or cleared. Keyring/secrets adapters must eventually cover lookup, fallback, migration, policy and multi-resource recovery as one qualified unit; do not implement ad-hoc key deletion from a guessed service name.

S-001 · MUST

Workspace boundary warning

Before first capture and each switch between differently labeled trust domains, state: "This changes the account, not the local history or workspace. Existing conversations and files remain here. Continuing a conversation may send its context under the selected account." Require explicit acknowledgement for cross-domain switches; do not remember a blanket waiver.

S-002 · MUST

Authorized use only

Manage only accounts the owner is authorized to use. Never bypass forced-workspace/login policy, device authorization, account suspension or access controls. A policy mismatch yields E_POLICY_DENIED, not a suggestion to choose another route.

Protected does not mean inaccessible

05 · Vault, identities and generations

Save the newest usable session, not a permanently frozen copy of the first login.

S-003 · MUST

Opaque credential preservation

Capture exact bytes of every qualified auth resource, including unknown fields and absence. Parse a bounded copy only to validate supported shape and extract display/identity metadata. Do not normalize, pretty-print or reconstruct auth.json during switching. Reject malformed JSON, duplicate keys, invalid UTF-8, over-limit payloads and unsupported auth modes. v0.1 bounds are 1 MiB per auth resource, 4 MiB per complete credential set and a maximum JSON nesting depth of 64. Crossing a bound is unsupported input, not permission to truncate or raise limits silently.

Acceptance evidenceT-08 T-11
S-004 · MUST

Identity is not email

Use a random profile UUID for paths. Separate principal subject/user ID from workspace/account ID and issuer. Labels and email are display data, never uniqueness keys or filesystem components. Evidence must distinguish local decoded claims, official-runtime observations and human Desktop confirmation. Missing or ambiguous stable identity requires guided reauthentication or unsupported status, not email-only acceptance.

Acceptance evidenceT-12
S-005 · MUST

No concurrent token ownership

Never refresh inactive profiles in the background. During a switch, all shared-home clients must be closed before the outgoing snapshot is captured. Immediately before each replacement, compare current resources with the expected generation. If the active credentials changed normally since last capture, save that current generation; if the principal changed externally, ask the user to capture/reconcile it before switching.

Acceptance evidenceT-13 T-14
S-006 · MUST

Protected vault

Use a random 256-bit root key. Windows: protect it with current-user DPAPI, never CRYPTPROTECT_LOCAL_MACHINE and never deprecated interactive prompt mode. macOS: use a non-synchronizing Keychain item with the strongest compatible accessibility/access policy verified in Q0. Derive context-separated encryption and fingerprint keys using a reviewed standard KDF. Encrypt registry, identity metadata, credential generations and journals with a vetted AEAD implementation, binding schema/profile/generation/resource metadata as authenticated data. No homemade cryptography.

Acceptance evidenceT-15 T-16
S-007 · MUST

Nonce and key lifecycle

Use fresh OS-random nonces with the selected AEAD’s required length, never a resettable local counter. Declare algorithm, key ID and envelope version. Immutable credential generations must not be overwritten in place. Vault-key loss means official reauthentication, not a backdoor recovery key. A future key migration is a separately tested transactional migration.

Acceptance evidenceT-15
S-008 · MUST

File protection

Vault roots must be local, user-owned and not known cloud-sync/network locations. Windows uses a protected DACL restricted to the owner and required SYSTEM access; no broad inherited read grants. macOS directories use 0700 and files 0600. Validate ancestors, ownership, reparse/symlink and hardlink hazards via handle-based APIs. A blanket chmod is not a substitute for safe path traversal. Refuse unsafe paths instead of repairing arbitrary user files.

Acceptance evidenceT-17
S-009 · MUST

Bounded retention and deletion

Keep the latest inactive generation plus generations referenced by an unresolved transaction. After a clean terminal state and a verified later startup, prune unreferenced older generations. Never auto-expire an unresolved recovery record. Removing an inactive profile removes its registry references and local encrypted generations; it does not revoke the provider session. Refuse deletion of the active profile until another profile is installed or the user signs out in the official client.

Acceptance evidenceT-18

Honest erase semantics

Do not promise secure erasure on SSDs, snapshots, backups, swap or crash dumps. No plaintext vault export, clipboard copy, cloud sync or portable bundle is in v0.1.0. Reauthentication is the supported migration path to another machine. Memory zeroization is best effort, including parser buffers and OS-returned allocations, not a claim that secrets never exist in RAM.

06 · Process and filesystem safety

Closing the visible window is not sufficient proof that every credential writer has stopped.

F-009 · MUST

Single transaction

Acquire an OS lifetime-scoped lock per owner and canonical target home before any capture/login/switch/recovery operation. Reject a second transaction with E_BUSY. Use a kernel lock, not only a stale lock-file marker. Hold it through helper shutdown, durable outcome and relaunch decision.

Acceptance evidenceT-14
F-010 · MUST

Quiesce the affected set

Enumerate the qualified Desktop process tree and other known Codex CLI/IDE/runtime writers sharing that home. Ask once to close the selected Desktop, with active-work warning. Send its normal OS quit request; wait up to 30 seconds. Other clients are listed for the owner to close manually. Do not kill all node/Electron processes, all terminals, or whole IDEs. If writers remain or cannot be identified confidently, stop before auth changes.

Acceptance evidenceT-19
F-011 · MUST

No force bypass

No --force, hidden setting or developer-mode override may bypass writer/policy/backend/path checks in a distributable build. An owned helper may be terminated after its timeout; user-owned applications may not. Termination must be followed by a bounded exit wait and descendant check. A successful signal call is not proof of exit.

Acceptance evidenceT-19 T-20
F-012 · MUST

Narrow durable writes

Stage each replacement in the destination directory with secure permissions from creation. Flush contents, use the qualified OS atomic replacement primitive, verify resulting ownership/ACL and content, and persist directory/metadata durability using the qualified platform primitive. Do not truncate live auth in place, use a cross-volume rename, or retain plaintext .bak files. Preserve an absent original as an explicit state.

Acceptance evidenceT-21 T-22
F-013 · MUST

Multi-resource integrity

Atomic rename covers one file, not a credential set or registry. Journal intent before each resource replacement and completion after it. Keep clients closed for the entire set operation. Track a presence bitmap and keyed fingerprints so a crash between auth.json and a qualified companion is detectable. The generic coordinator is not licensed to discover and edit additional files.

Acceptance evidenceT-08 T-22
F-014 · MUST

Detect unexpected writes

Repeat process discovery and handle-based resource checks before applying the first replacement and before helper launch. During the bounded transaction, watch for file-generation changes as an additional signal. A conflicting writer or unexpected byte change yields E_EXTERNAL_CHANGE; preserve encrypted evidence and do not overwrite it. State explicitly that monitoring cannot make an uncooperative external process obey our lock.

07 · Adding and refreshing accounts

The official runtime owns the sign-in ceremony. The switcher never asks for a password or pasted bearer token.

F-015 · MUST

Capture current account

Capture requires a qualified file backend and quiescent shared-home clients. Read the live resources once into a bounded secure buffer, validate identity, encrypt a new generation, durably commit registry metadata and show a non-secret account summary. Capture must not replace active auth. An existing matching principal/workspace updates its current generation after explicit acknowledgement; duplicate exact sessions may not become independent profiles.

Acceptance evidenceT-11 T-12 T-24
F-016 · MUST

Add via official login

Create a random owner-only staging home under the protected application root and a durable encrypted onboarding record. Launch the approved official runtime with that home, a safe application-owned working directory and only the qualified effective auth/policy context. Do not copy arbitrary user hooks, MCP or workspace config, and do not strip managed restrictions. If the required policy context cannot be reproduced safely, block this path.

Acceptance evidenceT-03 T-24
F-017 · MUST

Login commit and cancel

Start the official managed browser login; show its URL only through a native browser-open action after scheme/host validation against the qualified official endpoint set. Do not use an embedded login browser. After a matching successful login completion, stop and reap the helper, capture the resulting credential generation, encrypt it and commit the new profile. The live Desktop home remains unchanged. On cancel/timeout, request login cancellation when available, stop/reap the helper, clean staging and retain recoverable encrypted state if cleanup failed.

Acceptance evidenceT-20 T-24
F-018 · MUST

Reauthenticate without token replay

A needs_login profile gets a fresh official login in staging. Require that the resulting principal/workspace matches the intended profile; otherwise offer a new profile rather than overwriting it silently. Revoked or rotated-out saved tokens are never resurrected from older backups. Do not call official logout as an implementation of switching.

Acceptance evidenceT-12 T-13 T-24

Staging exposure

Official file-mode login temporarily writes plaintext into its staging home. Protect it like live auth, never send its contents to the frontend, and inspect unresolved onboarding records before any new operation. If the owner will not accept this exposure, file-mode switching is not appropriate; do not hide it behind the encrypted-vault claim.

08 · Official-runtime protocol

Use a small, bounded subset of an explicitly qualified runtime protocol.

S-010 · MUST

Approved subprocess only

Run a bound absolute executable with an argument array and no shell. The baseline documented launch is app-server with default stdio, or an explicitly qualified --listen stdio:// option; do not copy a third-party --stdio flag without verifying it. Sanitize inherited credentials, runtime overrides and loader/debug variables using a reviewed environment policy that retains required OS/enterprise context. Never connect to guessed Desktop control sockets.

Acceptance evidenceT-04 T-25
S-011 · MUST

Bounded framing

Use newline-delimited JSON on private stdio pipes. Cap each frame at 1 MiB, aggregate pending data at 4 MiB and pending notifications at 32. Drain stderr independently without forwarding raw text; keep only allowlisted structured error categories. Match response IDs and login IDs; tolerate notification/response reordering. Reject duplicate JSON keys, malformed frames and unexpected privileged server requests. No unbounded read-to-end or unbounded wait.

Acceptance evidenceT-25 T-26
S-012 · MUST

Method allowlist

The coordinator may use initialize, initialized, account/read, account/login/start in managed mode, account/login/cancel, account/rateLimits/read, and the qualified read-only configuration/requirements methods. It may observe login/account notifications. Reject arbitrary RPC requests from the UI. No thread, turn, command execution, filesystem, MCP, credit-consumption, logout, external-token or remote-host operations.

Acceptance evidenceT-01 T-25
F-019 · MUST

Refresh ownership

Local inspection requests do not force refresh. A user-selected online credential check may let the one owned official helper perform its normal auth maintenance. After every helper run that could write, stop/reap it and capture resulting live or staging bytes into a new encrypted generation before any rollback or subsequent switch. Runtime startup and rate-limit reads must be tested for side effects.

Acceptance evidenceT-13 T-20 T-27

Handshake and version binding

Generate the version-specific schema from the approved executable during qualification; pin its hash with the adapter. Complete initialize response handling before initialized and account operations. The documented account/read example exposes email/plan, not a universal stable-workspace proof. Never synthesize missing identity fields. [O3] defines the public starting point; exact installed behavior is a Q0 deliverable. O3

Offline and online defaults

Switching defaults to bounded local inspection plus explicit confirmation in the reopened Desktop. Any helper operation that may contact OpenAI or refresh tokens requires user approval for that operation and the qualified adapter must document its network effects. An offline timeout is observation unavailable, not proof that saved credentials are invalid. The coordinator may complete installation and relaunch while leaving credential acceptance unknown and Desktop identity awaiting confirmation. There is no inactive-account polling.

09 · Switch transaction

The filesystem commit is real. The UI confirmation is a separate observation.

Transaction record

An encrypted, atomically replaced journal holds transaction UUID, operation, selected target, original identity/generation, expected live resource fingerprints, staged target generation, resource-intent/completion bitmap, helper ownership, commit state and sanitized outcome. It never stores absolute paths or IDs in plaintext diagnostics. A durable record must exist before any externally visible auth write.

F-020 · MUST

Preserve before replace

The latest outgoing live generation MUST be durably encrypted and reachable before the first target resource changes. A registry marker from last week is not the source of truth. Unsaved external logins require capture or cancellation, not silent discard.

10 · Crash and conflict recovery

Recovery preserves information first. It never guesses that an old token is still valid.

F-024 · MUST

Recovery first on startup

Acquire the same home-scoped lock and inspect incomplete switch/onboarding records before enabling mutations. Re-establish process quiescence before restoring anything. No automatic replacement while Desktop, its helper or another possible writer is alive. A stale PID must be matched against process start identity before any action.

F-025 · MUST

Restoration is itself transactional

Use a recovery sub-operation in the existing journal with source and target generation references, intent/completion states and integrity checks. Keep the original failure plus restoration outcome. Crash injection must cover every restoration write just as it covers the forward path. A failed restoration must not replace the primary error with a generic message.

11 · User interface and command boundary

A small account picker should make authority and uncertainty obvious.

Main window

Show selected installation and backend at the top. Account cards display owner label, optionally masked email, workspace label when actually known, last captured time and health. Actions: Add account, Capture current, Switch, Rename, Reauthenticate, Remove inactive and Diagnostics. A tray/menu-bar list may mirror the same metadata and switch intent. No dashboard of prompts, cost estimates, session content or automatic recommendations.

Status vocabulary

Use Available, Login required, Unsupported backend, Clients still running, Credentials installed, Online check unavailable, Desktop opened, Check account in Desktop, User-confirmed, Conflict needs review and Recovery required. Unknown quota is not zero. Unknown workspace is not Personal. Installed is not Verified.

S-013 · MUST

Intent-only renderer

Expose only typed metadata reads and enumerated intents. The frontend cannot supply raw paths, executable names, shell strings, RPC methods, tokens or arbitrary URLs. Rust validates profile/transaction IDs and current state on every call. Native confirmation shows immutable resolved source/target labels and application impact before mutation. A renderer-provided consent=true flag has no authority.

S-014 · MUST

All cases use fabricated credentials unless explicitly marked owner-run real integration. No test may turn a fake receipt into a production qualification.

14 · Errors and future boundaries

Every failed operation explains what changed and what did not.

ErrorMeaning / required action
E_BUSYAnother operation owns this target home; do not retry in a tight loop.
E_COMPAT_UNKNOWNInstallation/home/schema/backend behavior lacks a qualified record; no auth writes.
E_POLICY_DENIEDEffective policy forbids the target or policy evidence is incomplete; no bypass.
E_BACKEND_UNSUPPORTEDKeyring/auto/secrets/ephemeral or other unsupported auth mode; do not switch to file mode automatically.
E_CLIENTS_RUNNINGA relevant writer remains; user closes it before retry.
E_HELPER_STUCKOwned helper/descendant did not exit; stop mutations and show recovery state.
E_VAULT_LOCKED / E_VAULT_CORRUPTUnlock or restore trustworthy application storage; leave live auth unchanged.
E_PATH_UNSAFEOwnership, location, ACL or link semantics violate the path contract.
E_EXTERNAL_CHANGEObserved live resources changed unexpectedly; preserve, reconcile, never clobber.
E_LOGIN_REQUIREDProvider/runtime rejects saved login; official reauthentication required.
E_OBSERVATION_UNAVAILABLEOffline/timeout/incomplete identity observation; do not relabel as invalid credentials.
E_WRITE_FAILED / E_RECOVERY_REQUIREDPartial operation may exist; show precise recorded stage and restore options.
E_LAUNCH_FAILEDTarget credentials may already be committed; offer open/retry rather than stale automatic rollback.

Explicitly deferred

Keyring/secrets-backed active Codex auth requires a separately qualified adapter and transactional design; per-profile Desktop homes require proof of package launch and history behavior; Linux/WSL require native evidence. Quota monitoring can be a read-only future module only after refresh ownership is solved. None of these may be added as a side effect of implementing v0.1.0.

Never implied

No guaranteed seamless mid-task handoff, no subscription limit bypass, no isolation of shared history, no protection from administrator or same-user malware, no irreversible credential erasure, no verified Desktop identity from a helper-only check, and no security guarantee from stars, notarization, source availability or self-building alone.
